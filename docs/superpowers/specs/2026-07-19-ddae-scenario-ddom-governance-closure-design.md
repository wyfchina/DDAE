# DDAE 场景可行性与 DDOM 治理闭环整改设计

日期：2026-07-19  
状态：用户已要求集中整改，按既有授权直接进入实施  
目标分支：`codex/scenario-ddom-governance-closure`  
设计基线：`d876139`

## 1. 目标

集中修复“未来场景模拟”到“DDOM 配置决策”的四类断点：

1. 内部演示主数据、粗能力时间桶和预算基准量级失配，导致所有内置方案在默认综合平衡下必然被阻断。
2. 可行性状态与保存状态被拼成“阻断采纳，未保存”，让用户误以为红色方案不能保存留痕。
3. 采纳规则由前端硬编码且口径分叉，“供应优先”可以绕过能力、服务等硬红线。
4. 保存候选后缺少“人工选定—原子变更包—白盒复算—验证门禁—人工审批”的持久化闭环，刷新后还会丢失页面内存中的比较上下文。

完成后的业务链为：

`冻结基线 → 场景比较 → 保存候选 → 人工选定 → 创建 DDOM 变更包 → 人工提交 → 白盒复算验证 → 人工评审/批准/生效 → 行动与结果验证`

## 2. 边界

- 所有改动只发生在 DDAE 仓库和 DDAE 内部 API、领域模型、SQLite、种子数据与业务页面。
- 不修改 `DDAE_INTERFACE_CONTRACT`、SDBR 接口字段、状态、ACK、错误码、JSON、样例、端点或契约测试。
- 不修改 `DDAE-NetworkStructure`，不读取或解释网络评分。
- 不增加外部导入、连接器或协议适配器。
- 不生成执行排程。四周 RCCP 工作窗口只是聚合工作量的粗能力时间桶，不产生工序顺序、开工时刻或下达指令。
- 不自动选定、提交、评审、批准、生效或发布任何结果。
- 白盒追踪和公开演示闭环页面、DOM、按钮、端点及协议行为保持不变。
- 已冻结基线、已保存场景、已保存变更包和验证记录不可覆盖；修订方案必须创建新记录。

## 3. 已确认根因

### 3.1 粗能力量级

现有第 1 周热真空试验舱负荷为：

`85×8 + 93×3 + 37×25 + 132×1 = 2016 小时`

周能力只有 96 小时，因此负荷为 2100%。AIT 同周为 `2686/160 = 1678.8%`。这不是百分比格式错误，而是大 MOQ 补货批次、单件路由工时、周能力标尺和“全部落在释放周”的算法共同造成。

### 3.2 流速与预算

- 平均资源负荷超过 250% 后，流速公式长期被钳制在下限 40，无法区分响应方案。
- 预算基准只使用 `ADU×DLT×成本×1.4`，未使用冻结基线的在手和已确认在途事实，使演示库存被判定为约 1270% 超支。
- 当前四个模板没有处理产生峰值的时间窗口；“MOQ 与订货周期调整”反而把 MOQ 提高 20%。

### 3.3 状态和治理

- “阻断采纳”是采纳判断；“未保存”只是当前预览尚未留痕，两者没有因果关系。
- 红色但证据完整的候选必须允许保存，用于审计、协调和修订；只有物理库存证据缺失才禁止保存。
- 已保存场景只有 `Saved / NotSubmitted`，没有受审计的候选选定状态。
- DDOM 建议逐条保存，无法证明一组变化与一个已验证场景完全对应。
- 单条主设置变更可以在没有最新白盒验证的情况下推进到批准和生效。
- 刷新后前端无法从 SQLite 恢复完整比较对象，DDOM 入口错误依赖 `savedFutureComparisons` 内存对象。

## 4. 选择的整改方式

### 4.1 未采用的方案

**只放宽阈值**：不采用。它会把 2100% 能力和 1270% 预算量级问题伪装成可接受方案。

**引入完整有限能力排程**：不采用。它超出 DDS&OP 战术模拟边界，并会触及执行排程职责。

### 4.2 采用的方案

采用“内部标尺校准 + 后端统一可行性规则 + 原子 DDOM 变更包”的组合方案：

- 校准 DemoFixture 的 MOQ、已验证周能力和预算基准。
- 将补货批次的 RCCP 工作量均摊到固定四周粗能力窗口，保持工作量守恒并明确标注“非执行排程”。
- 由后端产生权威可行性评估，前端只展示。
- 保存、候选选定、可行性和治理使用四条独立状态轴。
- 一个 DDOM 变更包只允许来自一个已选定场景；若需要组合不同措施，必须先在第 03 阶段形成一个组合响应并保存。
- 变更包保存最终 `ScenarioRunPreviewRequest` 与 `ScenarioRunParameterSet`，以后端保存值为复算权威输入。

## 5. 内部演示标尺

### 5.1 MOQ

MOQ 调整为覆盖约一至两周演示需求的量级：

| SKU | MOQ |
| --- | ---: |
| SAT-BUS-001 | 2 |
| SAT-BUS-002 | 2 |
| SAT-PROP-003 | 6 |
| PAY-EO-101 | 2 |
| PAY-SAR-102 | 2 |
| AV-COM-201 | 12 |
| AV-OBC-202 | 8 |
| AV-FPGA-203 | 5 |
| TC-MLI-301 | 30 |
| TC-RAD-302 | 20 |
| MECH-DEP-401 | 8 |
| CBL-HAR-402 | 30 |

FPGA 的 MOQ=5 继续作为统一内部主数据。

### 5.2 已验证周能力

内部演示周能力调整为：

| 资源 | 周能力工时 |
| --- | ---: |
| RES-AIT | 370 |
| RES-TVAC | 185 |
| RES-CLEAN | 120 |
| RES-HARNESS | 460 |

这些值由完整四周窗口下的内部演示峰值工时校准，并保留少量可用余量；只用于 DDAE DemoFixture，不是 SDBR 或外部主数据，也不得外推为实际工厂产能。校准后默认峰值约为 98.9%，受限模板仍通过明确的容量损失越过 100% 硬线，确保同时存在可评审与阻断示例。

### 5.3 四周 RCCP 工作窗口

每笔投影补货订单的 `数量×单件资源工时` 使用一个完整、连续且位于展望期内的四周粗能力窗口等额分摊。订单周是补货释放压力的聚合起点：正常从订单周向后覆盖四周；接近展望期末时将完整窗口整体左移到展望期内，不得截断后把工作量挤压到最后一周。每笔订单的总工作量必须守恒。

示例：第 1 周一笔 100 件、每件 1 小时的订单，在第 1 至第 4 周各产生 25 小时粗能力需求；不得再全部压在第 1 周。

同理，第 12 周的同一订单在 12 周展望期内分摊到第 9 至第 12 周，每周 25 小时；不得因展望期末截断而把 100 小时全部压在第 12 周。该窗口只是粗能力聚合，不形成工序顺序、开工日期或执行排程。

该窗口不计算工序开始时间、优先级、机器分配或执行顺序。

### 5.4 预算基准

每个产品族的库存预算基准使用冻结事实：

`Σ((在手库存 + 已确认在途) × 单位成本) × 1.10`

预算记录继续按周输出，但来源值固定为同一冻结基线，不从未来结果倒推。界面必须说明来源为“冻结基线库存与已确认在途”。

### 5.5 模板可达性

- 提前建库模板的建库周必须早于被保护的第 6–8 周需求窗口。
- 能力缓解模板作用于实际高风险窗口和相关资源，倍率保持 1.15–1.25，不允许用不合理倍数刷绿。
- 订货策略模板降低目标 SKU 的 MOQ，并缩短订货周期，不再把 MOQ 提高 20%。
- 受限模板保留明确的能力或供应红例。
- 默认演示必须至少有一个“可评审”或“待协调评审”候选，并至少有一个“阻断”候选。

## 6. 后端权威可行性评估

新增内部 `ScenarioFeasibilityPolicy`。`ScenarioRunPreviewResult` 增加可选 `Feasibility` 字段，保存结果时一并持久化。前端删除自行决定最终结论的 `evaluateAdoption` 规则，只保留旧记录的只读兼容显示。

### 6.1 状态

- `Adoptable`：所有硬红线通过，且没有黄色协调项。
- `Reconcile`：所有硬红线通过，但存在黄色协调项，可提交 DDOM 评审。
- `Blocked`：至少一条硬红线失败，不可选定为 DDOM 候选，但仍可保存留痕。

### 6.2 统一硬红线

所有优先模式都必须检查：

- 基准与方案的物理库存证据完整；
- 服务相对产品族目标的缺口不超过 3 个百分点，且相对基准下降不超过 3 个百分点；
- 峰值粗能力负荷不超过 100%；
- 供应缺口占需求比例不超过 15%；
- 方案平均库存金额相对基准增幅不超过 12%；
- 任一 SKU 连续处于红区不超过 3 周。

黄色协调线来自现有业务栅栏：服务缺口超过 1 个百分点、能力负荷超过 85%、供应缺口比例超过 5%、平均库存增幅超过 5%或连续红区超过 1 周。流速目标偏差作为比较和协调指标，不再与能力负荷重复形成第二条硬阻断。

`Balanced/ServiceFirst/FlowFirst/CashFirst/CapacityFirst/SupplyFirst` 只改变黄色检查排序、摘要和建议动作优先级，不能删除或绕过任何硬红线。

## 7. 四条独立状态轴

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 证据 | Complete / EvidenceMissing | 缺失时禁止保存与治理 |
| 可行性 | Adoptable / Reconcile / Blocked | 后端白盒评估结论 |
| 候选 | Candidate / Selected / Superseded / Withdrawn | 人工是否选定为 DDOM 来源 |
| 治理 | Draft / Submitted / Reviewed / Approved / Effective / Expired | DDOM 变更包人工状态 |

保存状态继续使用 `Saved`。页面分别显示“可行性”和“留痕”，不得再输出一个混合 chip。

## 8. 候选选定

`scenario_runs` 增量增加：

- `candidate_status`
- `feasibility_status`
- `selected_by`
- `selected_at_utc`
- `selection_note`

新增人工选定操作：

- 只允许选择已保存、来源基线已冻结、具有 `baseline_snapshot_id / external_scenario_id / response_id` 且可行性为 `Adoptable` 或 `Reconcile` 的运行。
- 同一冻结基线和外部场景下选择新候选时，原 `Selected` 候选变为 `Superseded`。
- `Blocked` 候选只能保存、创建协调事项或回到场景修订，不能被选定。
- 选定、替代和撤回均追加场景审计事件。

## 9. DDOM 原子变更包

新增 `DdomChangePackageService` 和三张增量表。

### 9.1 `ddom_change_packages`

保存包编号、名称、来源基线、来源场景运行、外部场景、响应方案、治理状态、验证状态、最终请求 JSON、最终参数 JSON、输入指纹、负责人、审批人、生效/失效/复查日期、预期效果、回滚条件、创建人与时间。

### 9.2 `ddom_change_package_lines`

保存包内全部建议行：顺序、设置类型、目标、当前值、建议值、触发原因、风险、服务/现金影响和完整建议 JSON。包内行不能单独推进状态。

### 9.3 `ddom_change_package_validations`

每次验证追加保存：验证编号、包 ID、输入指纹、请求、结果、可行性结论、失败原因、trace、验证人与时间。最新验证可以覆盖包头的“当前验证状态”，但历史验证不可删除或覆盖。

包头验证状态固定为 `NotRun / Passed / Failed`；每条验证同时保存 `Adoptable / Reconcile / Blocked` 可行性结论。只有验证状态为 `Passed` 且可行性为 `Adoptable` 或 `Reconcile` 才满足评审门禁。

### 9.4 `ddom_change_package_audit_events`

只追加记录创建、提交、白盒复算、验证通过/失败、评审、批准、生效和失效。

## 10. 变更包流程和门禁

1. **创建 Draft**：只能从一个 `Selected` 场景创建；后端从 SQLite 读取保存请求和结果，重新生成全部建议行，前端不得提交计算结果或任意混搭建议。
2. **人工提交**：`Draft → Submitted`，提交后包内容不可修改。
3. **白盒验证**：后端读取冻结基线和包内最终请求，执行 `PreviewAgainstFrozenBaseline`，再执行统一可行性策略并追加验证证据。
4. **人工评审**：`Submitted → Reviewed` 只在最新验证状态为 `Passed`、可行性不是 `Blocked`、输入指纹一致且证据完整时允许。
5. **人工批准**：`Reviewed → Approved` 要求显式操作者，并在配置了审批人时与审批人一致。
6. **人工生效**：`Approved → Effective` 继续要求最新验证有效，且生效日期、复查日期和回滚条件完整。
7. **失效**：`Effective → Expired` 仍由人工执行。

系统不得自动调用任何状态推进操作。验证失败时包保持 `Submitted`，用户可以创建协调事项或回到第 03 阶段创建新候选和新包。

## 13. 界面

### 13.1 第 03 阶段

- 顶部筛选改为“计算范围”；场景表单“目标 SKU”改为“措施对象 SKU”。
- 显示只读范围摘要，明确计算范围影响汇总与后端重算，措施对象只影响具体动作。
- 分别显示：`可行性：可评审/待协调/阻断`、`留痕：未保存/已保存 SR-...`、`候选：未选定/已选定`。
- 红色证据完整方案仍可点击“保存候选”；保存后主操作为“创建协调事项并修订方案”。
- 黄色或绿色方案保存后显示“选定为 DDOM 候选”；选定后显示“进入 DDOM 配置决策”。

### 13.2 第 04 阶段

- 从已选候选创建一个变更包，不再要求页面内存保留原比较请求。
- 显示来源基线、场景运行编号、外部场景、响应方案、可行性、包内变化和最终参数摘要。
- 明确按钮：创建变更包、提交评审、运行白盒验证、标记已评审、批准、生效、失效。
- 每个不可用按钮显示缺少的门禁条件。
- 刷新后从 SQLite 恢复候选、包、验证和审计。

### 13.3 第 05 阶段

- 行动事项可以关联 DDOM 包。
- 红色候选和失败验证可一键带入场景、包及失败原因，但仍由用户确认创建。

保持深绿导航、白色顶部条、浅灰画布、8px 卡片、现有 chip、表格和抽屉体系，不引入新前端依赖。

## 14. 错误处理

- 证据缺失：只允许预览，不允许保存或进入治理。
- 红色阻断：允许保存，不允许选定；返回全部违反项。
- 非冻结基线、缺少谱系或请求内容不一致：拒绝选定和创建包。
- 包未提交：拒绝验证和评审。
- 最新验证失败或输入指纹不一致：拒绝评审、批准和生效。
- 审批人不匹配：拒绝批准并写明预期审批人。
- 旧记录缺少新增字段：按 `Legacy/NotRun/未关联` 只读显示，不猜测或回填。

## 15. 验收

- 259 项现有基线测试继续通过，并增加针对本设计的测试。
- 四周粗能力测试证明每笔订单工作量守恒，且不是单周集中。
- 默认演示基线峰值负荷不超过 100%，平均负荷处于可信范围，流速不再固定为 40。
- 至少一个内置候选为 `Adoptable` 或 `Reconcile`，至少一个为 `Blocked`。
- 六种优先模式均不能绕过相同硬红线。
- 红色且证据完整的方案可保存但不能选定；证据缺失才禁止保存。
- 页面刷新或服务重启后，已选候选仍能创建、查看并验证 DDOM 包。
- 包未通过最新白盒验证时不能进入 `Reviewed`；通过后仍必须人工逐步推进。
- 行动结果不会自动批准、生效或修改冻结基线。
- 完整测试通过；`dotnet build AdaptiveSopDdsop.sln --no-restore -m:1` 为 0 warning、0 error。
- 最终差异和保护脚本证明 SDBR、CONTRACT、Network、白盒追踪与公开演示闭环未变化。
